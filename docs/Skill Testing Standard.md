# Skill Testing Standard

## Status

Authoritative. This document elaborates `context/skills/Skill Testing & Evaluation Standard.md` (the short scenario-category list) into concrete evidence requirements: what scenario categories a Skill's test coverage must include, the minimum fixture bar a Skill must clear at the Tested stage before it can be certified (`docs/Skill Taxonomy.md` Section 7, stages 3 and 5), and how the two testing tiers already in use elsewhere in this repository apply to Skills specifically. It does not redefine `context/skills/Skill Testing & Evaluation Standard.md`'s scenario list — it is restated here only because the minimum-bar and evidence-tier rules below depend on it.

## 1. Two Testing Tiers — Which Applies to a Skill

Engineering Mentor already has two genuinely different kinds of test evidence, established by `tests/schema-tests/README.md` and `tests/skill-tests/code-review/README.md` respectively. Neither is a placeholder for the other; a Skill uses whichever tier fits what's actually being verified, and states which in its own test directory's README where that isn't obvious.

- **Deterministic.** A fixture plus an `*.expected.json` sidecar, checked by a script with no LLM judgment involved (`scripts/run_project_yaml_tests.py`, `scripts/run_rules_and_exceptions_tests.py`, `scripts/run_governance_evaluation_tests.py`, and — as of this Standard — `scripts/run_skill_standard_tests.py`). This tier applies to anything with a machine-checkable structural or logical contract: a Skill's own frontmatter/section-presence structure (`scripts/validate_skill.py`), or a Skill that wraps a deterministic script the way `context-discovery` and Governance Evaluation do.
- **Narrative/regression.** A fixture specification — realistic input material plus pass criteria and named fail signals — run by loading the Skill's material into an agent and checking its output against the criteria, exactly as `tests/skill-tests/code-review/README.md` documents and exactly as honestly: **these are not automated assertions**, and a Skill's test suite must not claim otherwise. This tier applies to anything requiring judgment: whether a Review-type Skill correctly classifies a finding's severity, whether an Authoring/Workflow-type Skill produces a contract that actually satisfies a stated requirement, whether a Domain Pattern Skill's guidance is applied sensibly to a novel case.

**Evidence strength within this tier is not uniform.** A narrative fixture existing, carrying a stated pass/fail criterion, and being structurally validated by `scripts/validate_skill_test_evidence.py` (category diversity, non-empty scenario files) is real evidence — but it is evidence that *the fixture is well-formed*, not evidence that the Skill actually produces the passing behavior the fixture describes. That confirmation requires one of: the fixture actually executed against a live model invocation of the Skill with the output checked against its pass criteria, or an independent reviewer's own read of the Skill's material against the fixture reaching the same conclusion. A well-formed, category-complete, structurally-valid fixture set must not be reported or relied on as if it were confirmed-passing behavioral evidence — those are different claims, and this Standard deliberately keeps them distinguishable rather than letting fixture completeness stand in for execution. **Proposed addition (Phase 15, not yet adopted by any actual certification):** this section defines Tier D and Tier E conceptually but does not state a minimum Tier D fixture count/diversity, a Pass-Criteria-withholding procedure, an evidence-recording format, or what "independent" means for Tier E — `docs/Skill Certification Process.md` Sections 6 and 7 propose concrete minimums for both, without altering either tier's definition as stated here. **Policy clarification (Phase 19):** Tier D/E minimums are gating requirements for the *optional* Certified lifecycle stage only (`docs/Skill Certification Process.md`'s policy clarification) - a Skill reaching Reviewed or Production under `docs/Skill Taxonomy.md` Section 7's normal internal path is not required to have Tier D or Tier E evidence; Tier A/B/C (fixture existence, expected results, structural validation) remain the ordinary bar those stages already require.

Most Skills beyond the simplest reference-only Domain Pattern content need narrative/regression coverage; a Skill wrapping a deterministic script additionally needs that script's own deterministic suite, but the Skill's *judgment* layer (when to invoke the script, how to interpret its output) still needs narrative coverage on top — `context-discovery` is deterministic underneath but the Skill layer around it (Section 3's postures, Failure Handling) is still worth narrative scenarios for the cases the script alone can't express (e.g. "the consuming Skill correctly falls back to direct inspection when `.mentor/` is absent").

## 2. Required Scenario Categories

Every Skill's test coverage — narrative, deterministic, or both — must include evidence for:

- Happy path
- Edge cases (drawn directly from the Skill's own `Edge Cases` section — an edge case named in the Skill but never exercised in a fixture is a gap in the fixtures, not an acceptable omission)
- Invalid input
- Missing required context (per this Skill's own `Required Context` posture, Section 3 of `docs/Skill Standard.md`)
- Ambiguous requests
- Conflicting requirements
- Existing-code / existing-repository scenarios (where applicable)
- Large inputs
- Failure scenarios (per the Skill's own `Failure Handling` section — same rule as edge cases: named there, exercised here)
- Security-sensitive scenarios, wherever the Skill's Category or content touches trust boundaries

**Additionally, for any Skill whose Governance Integration section (per `docs/Skill Standard.md` Section 4) states it invokes Context Discovery and/or Governance Evaluation** — i.e. every Review-type Skill and any Authoring/Workflow-type Skill that can surface a governance-classified finding — test coverage must include the governance-relationship categories `skills/code-review/SKILL.md`'s own fixture suite already establishes as the reference set: a Compatible relationship, an Additive (Child Mandatory adds to Mentor Mandatory) relationship, a Prohibited Override attempt, a genuine Override (a Child Advisory rule legitimately replacing Mentor Advisory guidance, per `docs/Governance Precedence Model.md` Section 8 — `tests/skill-tests/code-review/24-child-advisory-overrides-mentor-advisory.md` is the reference example), a genuine Conflict (two legitimate, applicable, non-Mandatory requirements that cannot both be satisfied and neither is a sanctioned override of the other, per `docs/Governance Precedence Model.md` Section 10 category 4 — `tests/skill-tests/code-review/27-child-mandatory-conflicts-mentor-advisory.md` is the reference example), a Child Advisory rule with no conflict, a rule outside its declared scope, a rule whose applicability can't be determined from available evidence, an applicable and an expired/inapplicable exception, an exception attempting a Mandatory security downgrade, and a scenario verifying governance classification and finding severity are scored independently. Override and Conflict are easy to omit because they are less common in practice than Compatible/Additive/Prohibited-Override — the Phase 12 independent certification pilot found all three of this repository's then-current Review-type Skill fixture sets (`security-review`, `database-review`, `api-review`) missing both, despite otherwise meeting this section's category list, precisely because the list above did not name them explicitly prior to this revision. Naming them explicitly here is intended to prevent a future Review-type Skill from inheriting the same gap by mechanically satisfying only the previously-named categories. A new Review-type Skill does not need to invent these scenarios from scratch — adapt `tests/skill-tests/code-review/`'s governance-fixture series (fixtures 11 through 26 in that README's table, not just the first ten of them) to the new Skill's own subject matter, the same way that series was itself written once and is the reference shape for every Review-type Skill after it. That table is the authoritative, current list; the categories named above are illustrative of its range, not an exhaustive substitute for it.

## 3. Minimum Fixture Bar Before Certification

A Skill cannot advance past the Tested stage (`docs/Skill Taxonomy.md` Section 7, stage 3), and is therefore not eligible for certification (stage 5), with:

- Zero fixtures of either tier — this is `mentor-skills-source`'s exact, uniform gap (`SKILL_QUALITY_REPORT.md` Section 7 of that audit: 0/5 test coverage across all 30 skills, with no exceptions) and is treated here as a hard blocker, not a scored-but-passable deduction.
- Happy-path-only coverage — a Skill tested only against the case where everything goes right has not been tested against the categories in Section 2, regardless of fixture count.
- For a Review-type Skill: fewer than the governance-relationship categories named in Section 2's second paragraph, when the Skill's Governance Integration section claims that posture. A Skill that claims to route findings through `evaluate_governance.py` but has no fixture exercising a Prohibited Override is claiming behavior it hasn't demonstrated.

There is no fixed minimum fixture *count* mandated here beyond covering every applicable category in Section 2 at least once — `code-review`'s 26 fixtures reflect that Skill's unusually large surface (general code review plus the full governance-relationship matrix), not a universal target every Skill must match numerically. A narrow Domain Pattern Skill with a small Edge Cases list may need far fewer fixtures to cover the same categories completely. Clearing this bar is a structural/coverage gate, not confirmation that the fixtures pass — see Section 1's evidence-strength note; a Skill can be fixture-bar-eligible (structurally Tested) without any narrative fixture having actually been executed, and that gap must be stated explicitly wherever this bar is used as part of a certification decision, not silently carried as if it were stronger evidence.

## 4. Regression Discipline

When a Skill's behavior is found wrong (during review, during use, or during a later audit): record the scenario as a new fixture in the appropriate tier before changing the Skill, confirm the fixture demonstrates the failure against the *current* Skill text, fix the Skill, and confirm the fixture now passes. Never fix a Skill's behavior without a fixture that would have caught the regression — this is `context/skills/Skill Testing & Evaluation Standard.md`'s own failure-handling sequence, restated here because Section 3's certification bar depends on it: a Production Skill's fixture count only ever grows.

## 5. Storage

Deterministic Skill-structure fixtures: `tests/schema-tests/skill/<name>.md` + `<name>.expected.json`, run via `scripts/run_skill_standard_tests.py` — see that directory's own README entry for the exact format. Narrative/regression fixtures for a specific Skill's judgment layer: `tests/skill-tests/<skill-name>/`, following `tests/skill-tests/code-review/`'s file-per-scenario, numbered, categorized shape (its own README table is the reference format).
